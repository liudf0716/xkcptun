04 监控5 / 16
05 · 根因 ①

每收一个包，flush 整个窗口：O(N²) 风暴

/* xkcp_server.c —— 每个收到的 UDP 包 */

重传堆积后，每个到达的包触发一次全窗口 flush（几百个段重新序列化发送）， 事件循环被自身流量饿死 → 内核收缓冲（仅 425KB）溢出 → 内核成批丢弃入包，包括我们苦等的 ACK → 更多 RTO 重传 → 更堵。恶性循环。

修复：ACK 交给 10ms 定时器统一 flush（延迟 ≤10ms，无感知），收包路径只做 input + 转发。

05 根因①6 / 16
06 · 根因 ②

EAGAIN = 丢包：C 与 Go 的哲学差异

Go (kcptun)

socket 写满时，运行时把 goroutine 停住 →
天然的阻塞背压，包一个都不少

C (xkcptun，修复前)

非阻塞 sendto 返回 EAGAIN →
直接丢弃，KCP 层以为发出去了

修复：用户态出口队列。EAGAIN 的包进 evbuffer 排队， 注册 UDP socket 的 EV_WRITE，可写时补发——对 KCP 完全透明，把「丢包」变回「排队」。

同时给 TCP→KCP 入口加背压：发送队列 >256 段暂停读 TCP（窗口回压源头），<64 段恢复。

07 阶段成果8 / 16
08 · 根因 ③

每 10ms 一次的窗口级突发

ikcp 的发送模型

每个 flush tick 倾泻整个窗口
1024 包 ≈ 1.35MB / 10ms 的脉冲
→ 打爆 transit 路由器浅缓冲 → 突发性丢包

实测代价

55%

批量传输中 55% 的发送段是重传
窗口满载，好put却被腰斩

修复：pacing —— 新配置项限制每个 tick 的发送段数（本次部署 128 段 ≈ 170KB）， 配额用尽即停、下个 tick 续发，对段状态零破坏。

重传率 55% → 6%，srtt 回到物理真值 153ms。

08 pacing9 / 16
09 · 同期优化

监控之外的三项机制增强

  • 丢包驱动 AIMD 限窗（losscntl）：重传时每 RTT 缩窗 ×0.75，空闲时加性增回。fast3 的 nc=1 不再盲目发射，窗口自动寻找平衡点
  • FEC 重构：部分填充的组 100ms 后立即补发 parity（小包交互不再裸奔）；parity 比例每 5s 按实测恢复率自适应，低丢包时冗余趋向 0
  • FEC 从负优化变正优化：修复前固定 30% 冗余在丢包雪崩上火上浇油（+13s）；修复后 A/B 实测反而提速（6.6s → 6.2s）

12 · 最优配置

当前推荐（两端一致，已在线运行）

{ "mode": "fast3", // nodelay=1, interval=10, resend=2, nc=1 "mtu": 1350, "sndwnd": 2048, "rcvwnd": 2048, "fec": 1, // 部分组 100ms 补 parity + 自适应冗余比 "pacing": 128, // 每 tick 最多 128 段 ≈ 170KB，削平突发 "crypt": "none", "nocomp": true }
  • losscntl（AIMD 限窗）：默认开启；坏时段自动收缩窗口，好时段恢复
  • 服务器内核：net.core.rmem_max / wmem_max = 16MB（kcptun 官方同样推荐）
  • 每项参数都有监控数据背书：xkcp_spy -h <ip> -c -t status
12 配置13 / 16
13 · 复盘

四条方法论

1 · 先埋点再调参

盲调窗口/FEC 三轮全部无效；一个 status 命令的导出数据，一眼定位 97% 重传

2 · 找最强的参照物

和 Go 版 kcptun 同参数硬碰硬，4 倍差距就是 3 个 bug 的坐标

3 · 同时段交叉测量

链路波动 4 倍以上，不交叉的对比全是噪声；看最差值不看均值

4 · 差异即线索

「Go 阻塞 vs C 丢包」「定时 flush vs 逐包 flush」——每个行为差异背后都是一个设计缺陷
