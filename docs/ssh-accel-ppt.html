常规对策（改端口 / fail2ban / 密钥认证）治标不治本：sshd 依然对全网可见。
xkcptun 的思路：让 sshd 只监听本机/内网，公网上只暴露一个 UDP 端口—— TCP 扫描器扫不到任何开放端口；UDP/KCP 流量需要正确的会话才能建立连接，入侵面大幅收窄。

痛点② 安全3 / 17
方案

架构：SSH 藏进 KCP/UDP 隧道

本地 (办公网) 公网 (只有 UDP 可达) 美国 VPS (bwg) [ssh 客户端] --TCP--> [xkcp_client :2222] ==KCP/UDP:9089==> [xkcp_server] --TCP--> [sshd :27334 仅本机可达] 绑定内网网卡 IP 监听 0.0.0.0:9089/udp 防火墙拒绝公网到 22/27334 的 TCP
  • 加速：KCP (fast3) + 可选 FEC 前向纠错 + 快速重传，用带宽换确定性，专治高丢包链路
  • 隐身：VPS 的 TCP 层对公网完全闭合，扫描器看到的是一个"沉默"的 UDP 端口；配合 crypt 加密与密钥认证，安全性不降反升
  • 通用：隧道里跑的就是普通 TCP，SSH / SFTP / 端口转发全部透明可用

搭建 · 步骤 1

构建：两端都从源码编译

# 本地与 VPS 各执行一次（依赖：cmake / gcc / libevent-dev） git clone https://github.com/liudf0716/xkcptun.git cd xkcptun && mkdir -p build && cd build cmake .. -DCMAKE_BUILD_TYPE=Release && make -j4 ls xkcp_server xkcp_client # 两个二进制，server 放 VPS，client 放本地
  • VPS 侧要求：libevent-dev；内核建议开 BBR（直连对照实验需要）：sysctl -w net.ipv4.tcp_congestion_control=bbr; sysctl -w net.core.default_qdisc=fq
  • 建议同步调大 UDP 缓冲：sysctl -w net.core.rmem_max=16777216 net.core.wmem_max=16777216

搭建 · 步骤 2

VPS 端：server.json 与 sshd 收口

// ~/xkcptun/server.json { "localinterface": "eth0", "localport": 9089, // KCP/UDP 监听，公网唯一暴露面 "remoteaddr": "127.0.0.1", "remoteport": 27334, // 转发目标 = 本机 sshd "mode": "fast3", "mtu": 1350, "sndwnd": 2048, "rcvwnd": 2048, "fec": 1, "pacing": 128, "crypt": "aes", // 生产环境务必加密（测试对比时用 none） "key": "你的强随机密钥", "nocomp": true } nohup ./xkcp_server -c server.json -f -d 3 &
  • 安全收口：防火墙只放行 UDP 9089 与必要的业务端口，封禁公网到 sshd 端口的 TCP： ufw deny in tcp to any port 27334（sshd 仍监听 27334，但只服务于隧道回环）
  • sshd 本身：密钥认证 + PasswordAuthentication no，双保险

搭建 · 步骤 3

本地端：client.json 与启动

// 本地 ~/xkcptun/client.json（参数与 server 端一致！） { "localinterface": "br0", "localport": 2222, // 本地 TCP 监听 = SSH 入口 "remoteaddr": "VPS公网IP", "remoteport": 9089, "mode": "fast3", "mtu": 1350, "sndwnd": 2048, "rcvwnd": 2048, "fec": 1, "pacing": 128, "crypt": "aes", "key": "同一个密钥", "nocomp": true } nohup ./xkcp_client -c client.json -f -d 3 & # 日常使用：SSH 目标指向本地隧道口 ssh -p 2222 root@本地网卡IP

注意 1：绑定 IP

client 绑定在 localinterface 的 IP 上（不是 127.0.0.1）。本例即 192.168.8.226:2222。ssh 命令要用这个 IP

注意 2：参数一致

mode/mtu/窗口/fec/pacing 两端必须一致，否则轻则性能打折，重则无法互通

流量模型：SSH = 交互小包 + 偶发批量。 所以分别测「交互延迟」（T2）与「单流吞吐」（T1）＋「长稳」（T4），并各取多轮。

原理9 / 17
性能对比 · T1 单流吞吐

T1：32MB 传输，交叉 5 轮

run() { local t0=$(date +%s.%N) ssh $2 'dd if=/dev/zero bs=1M count=32 2>/dev/null' | wc -c > /dev/null local t1=$(date +%s.%N); echo "$1: $(echo "$t1 - $t0" | bc)s" } for i in 1 2 3 4 5; do run direct "-o ControlPath=/tmp/mA bwg" # A 直连(BBR) run xkcptun "-o ControlPath=/tmp/mB -p 2222 root@192.168.8.226" # B 隧道 done
  • 为什么用 dd 管道：服务端生成数据经 SSH 流回本地，测的是"完整 SSH 批量传输"端到端吞吐；wc -c 校验字节完整
  • 对照组直连必须开 BBR：net.ipv4.tcp_congestion_control=bbr，证明隧道赢的是"最差体验"而非"对手没调优"

性能对比 · T2 交互延迟

T2：模拟打字手感

# 1) 先建立 SSH 连接复用（消除每次连接的握手，只测会话内往返） ssh -o ControlMaster=auto -o ControlPath=/tmp/mB \ -o ControlPersist=1800 -fN -p 2222 root@192.168.8.226 # 2) 复用连接上连续执行 20 条命令并计时 time (for i in $(seq 20); do ssh -o ControlPath=/tmp/mB \ -p 2222 root@192.168.8.226 true; done)
  • 必须复用：不复用测到的 = 完整 SSH 握手（3+RTT），不是交互延迟
  • 读数方式：总时间 ÷ 20 ≈ 每条命令毫秒数；理论下限 ≈ 2×RTT（约 320ms@160ms RTT），这是物理极限，隧道不可能突破
  • 样本量：正式对比建议 200 样本并输出中位数 / P95（小样本会被丢包重传噪声淹没）

性能对比 · T4 长稳

T4：512MB 长跑 + 会话健康采样

# 一条命令跑 512MB（约 1-2 分钟） time ssh <通道> 'dd if=/dev/zero bs=1M count=512 2>/dev/null' | wc -c # 传输进行到一半时，另开终端采样隧道会话健康度（执行 2-3 次） ./xkcp_spy -h 192.168.8.226 -c -t status → srtt [153ms] retrans [6%] state [0] # 判读标准见下
  • 健康标准：srtt 稳定在真实 RTT±100ms 内；retrans < 30%；state 为 0（非 -1）；无残留僵尸会话
  • 为什么测长稳：短传输可能"碰巧"不遇丢包；512MB 必然穿越多个丢包周期，暴露真实恢复能力
  • 双端留证：VPS 上同时 wc -l server.log 确认无错误风暴

实测中踩过的四个坑（帮你绕开）

  • ssh 127.0.0.1 被拒：client 监听绑定在 localinterface 的 IP 上，不在回环——用 网卡 IP 连接
  • 参数不一致 = 性能 cliff：两端 mode/窗口/fec/pacing 不一致时轻则降速重则异常，改配置必须两端同步并重启
  • 服务器 UDP 缓冲：默认 wmem_max 212KB 扛不住窗口级突发，rmem/wmem 调 16MB（一次性 sysctl，建议持久化）
  • 重启会话即失效：client/server 重启后需重连 SSH；脚本化部署时先 pkill 再启动，注意 pkill 模式别误杀自己的 ssh 会话
