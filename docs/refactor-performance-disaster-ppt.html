🕵️ 3. 破案排凶：重构引入的代码缺陷全景

逐行比对 1.08.516 与重构分支的底层网络流管线，我们锁定了关键故障点：

🛑 属于“改坏了原本正确逻辑”的代码倒退

  • 缺陷 ①：UDP 收包热路径误加 ikcp_flush（最致命的 $O(N^2)$ CPU 饥饿）
  • 缺陷 ②：TCP 读数据漏了 Flush & 移除动态 peeksize（导致 20ms 发送时延与流式大包死锁）
  • 缺陷 ③：硬编码 256 队列断水阀（XKCP_SND_QUE_HIGH）（上传时人为暂停 70 次）

⚠️ 属于“新增特性时设计不严谨”引入的 Bug

  • 缺陷 ④：10ms 高频定时器无差别遍历 1024 槽哈希表（导致 CPU 周期严重空转）
  • 缺陷 ⑤：静态隧道误触发动态代理协议头（导致 SSH 握手前几字节被污染）
  • 缺陷 ⑥：服务端连接 sshd 未设 TCP_NODELAY 且缓冲区过小（产生 Nagle 延迟与卡顿）

🔥 4. 致命元凶 ①：收包热路径上的 O(N²) Flush 灾难

重构时手滑加的代码 (client_handle_packet)
IUINT32 conv = ikcp_getconv(buf);
ikcp_input(task->kcp, buf, nrecv);
- ikcp_flush(task->kcp); // ❌ 致命负优化 xkcp_forward_data(task);
连锁反应链条：
高速下载每秒涌入 3000+ 个 UDP 分片 $\to$ 每收到 1 包都遍历并 Flush 包含数千包的发送队列 $\to$ CPU 陷入 $O(N^2)$ 饥饿 $\to$ 内核套接字接收队列溢出 $\to$ 本地大量丢包 $\to$ 疯狂重传雪崩！
历史版本 1.08.516 的神级警示注释：
"No ikcp_flush here: flushing the whole window once per incoming datagram is O(N^2) once retransmits pile up..."

在 UDP 驱动的高性能协议栈中，收包热路径必须严格保持 $O(1)$ 开销。Flush 操作只应在本地 TCP 产生新数据时，或者由 10ms 周期性时钟批量调度！

🐢 5. 致命元凶 ②③：发包断水阀门与固定缓冲区死锁

A. 256 队列断水阀（上传卡顿元凶）

修复前硬编码限流
- #define XKCP_SND_QUE_HIGH 256
+ int snd_que_high = max(256, kcp->snd_wnd);
if (kcp->nsnd_que > snd_que_high) {
  bufferevent_disable(bev, EV_READ); // 暂停读取
}

硬编码 256 导致 50Mbps 上传时本地 TCP 读取被强行暂停 70 余次（每次 10ms），彻底毁掉了上传速度。

B. 移除 ikcp_peeksize 导致接收死锁

错误做法：重构后为了省事，改用栈上固定 char buf[2048]。
后果：当 KCP 组装出超过 2048 字节的连续数据流时，ikcp_recv 直接报错返回 -3 (IKCP_E_BUFFER_SMALL)，数据卡在接收队列排不出去，连接直接死锁。
修复方案：恢复使用 ikcp_peeksize() 探测大小并动态分配缓冲区。

⚙️ 6. 缺陷 ④⑤⑥：高频空耗、动态头污染与 Nagle 延迟

④ 10ms 遍历 1024 槽

原版只有 100 桶，重构后扩展到 1024 桶。每 10ms 遍历一次导致 CPU 频繁空转。

优化：降频至 1 秒清理一次，空闲 CPU 从 16.6% 暴降至 1.3%！

⑤ 动态代理头污染

配置解析误将静态隧道当成动态代理，客户端多发了 8 字节目标头，破坏了 SSH 握手协议。

优化：严格区分静态/动态隧道，静态直传裸流。

⑥ 服务端 Nagle 延迟

服务端连接 sshd 未设 TCP_NODELAY 且输出缓冲仅 256KB，导致上传开局 - stalled -。

优化：建连即开启 NODELAY 并扩大缓冲至 4MB。

🌐 7. 意外收获：跨洋长肥网络（LFN）的窗口物理定律

在 50Mbps 真实家庭宽带 + 200ms RTT 环境下的实测矩阵：

上行窗口设置 25MB 下载实测 25MB 上传实测
上行 512 窗口 7.39s (3.38 MB/s) 13.52s (1.85 MB/s ❌)
上行 1024 窗口 🏆 7.19s (3.48 MB/s) 11.02s (2.27 MB/s) 🚀
上行 2048 窗口 8.41s (2.97 MB/s) 10.42s (2.40 MB/s)
上行 4096 窗口 8.14s (3.07 MB/s) 10.50s (无额外收益)
🏆 终极破局解：定向非对称窗口（Asymmetric Window）
• 服务端：sndwnd = 4096, rcvwnd = 1024（机房全速下发）
• 客户端：sndwnd = 1024, rcvwnd = 4096（吃满 50M 上行，承接千兆下行）

512 上行在 200ms RTT 下理论上限仅 28.6Mbps，无法吃满 50M 宽带；而 1024 窗口（57.2Mbps 容量）刚好完美饱和物理上行！

✨ 8. 终极体验升级：代码层内置黄金默认值（零配置）

为了彻底解决“用户配置繁琐、调错参数导致负优化”的问题，我们直接在 C 源码层将黄金基准固化为默认值：

代码内置默认值（xkcp_config.c）：
• mode = "fast3"（10ms 极速时钟，nc=1）
• fec = 1 (10:3)（30% 纠错冗余，0-RTT 重建）
• pacing = 0（关闭限流，最大突发吞吐）
• sock_buf = 16MB（防内核 Socket 丢包）
• 客户端默认 snd=1024, rcv=4096
• 服务端默认 snd=4096, rcv=1024
